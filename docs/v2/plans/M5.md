## Implemented behavior and validation

The actual Application loop runs the policy and the one input owner. Live input requires explicit opt-in, a current calibrated focused client, fresh frame/source identity and fresh Player/session data for every battle owner. UI intents can proceed without Player; a producer cannot disable battle prerequisites with an intent flag. Guards run after preemption releases and check freshness again after window queries. Default live F8 signals emergency stop; F9 signals pause/resume. Dry-run and replay construct no physical device or global hook.

The recording backend retains the newest 10,000 events by default and exposes total_events/dropped_events. Runtime.tick_hz caps continuously ready-source decision cadence using an injected stop-aware wait; schedules advance from completion, with no catch-up burst. Healthy capture timeouts still tick safety/deadlines. Timed releases are tick-driven, not hard real-time OS guarantees.

Recovery maps historical settings explicitly: recovery_settle_s holds S (3 seconds), recovery_reverse_s is a stationary wait (60), recovery_turn_s holds W (5), then three S taps, then recovery_forward_s is a stationary wait (10). Releases occur independently of sequence advancement. Source/geometry/Player loss cancels the sequence, and purchase dialogs pause for manual handling.

Search defaults now match the active source controller (.6/0/.02, limit30), rather than unused pilot gains. Pixel aim and angular search use positive target-minus-current error. This milestone uses separate proportional computations; M6 supplies independent stateful PID and route control. The policy exposes navigation.tick(app, observations, snapshot), navigation.reset(), and guarded policy.emit(...) for M6 integration.
