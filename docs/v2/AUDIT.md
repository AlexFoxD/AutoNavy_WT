## Active call graph

`autonavy.py:main` parses launcher flags, optionally runs preflight, and calls `run_application` → `load_application_main` → imports `start_prog` → `start_prog.main`.

Importing `start_prog` imports `toolkit.scn`, which creates and starts DXcam and a repeated capture worker at module scope; importing `pilot` resets vJoy at module scope; importing `firesystem` loads an asset, constructs input helpers/controllers, and sleeps. `start_prog.main` activates the game and repeatedly calls `end → quit → start → join → init → main_running`. `main_running` launches repeated pathfinder, fire, and collision workers and independently watches battle-end templates. `pilot.pathfinder` itself has an infinite loop despite being passed to a repeated worker. `main.py` is a second, independently runnable orchestration path with `skip1`, `skip2`, and `skip3` sentinel files.

`autonavy.py` already defers application import until execution and supports injected application loading for tests: **already present**, preserve the import-safe property when migrating. This does not make its delegated runtime import-safe. `start_prog.main`, `main.py`, and standalone fire/pathfinding/capture scripts have no common guaranteed cleanup path.

Actual outer return type is a tuple; successful components are lists and point elements are integer tuples (JSON output serializes tuples as arrays). The first component was empty in all successful probes. The `.pyi` describes it as optional `List[Jps.Vertex]`; do not rely on it being always empty.

The sampled path is ordered **from goal toward origin, excluding both endpoints**. Successful `jump` values duplicate points already in the path; appending them is unnecessary and damages sequence order. Adapter normalization should validate native shape/types/bounds, reverse interior points, and add requested endpoints. Distinguish `None` from `[]`; the latter is a valid adjacent route. Handle identical endpoints explicitly before the native call. Validate resulting adjacency/topology rather than sorting coordinates or using proximity to guess order. Broader randomized native parity, obstacle-corner behavior, pathological runtime, and cancellation remain additional validation; these short probes do not prove worst-case termination.

`MapGrid(height,width)` and `set_grid(x,y,type)` work on a rectangular grid as documented. Tile strings are exact protocol values `obstacle`, `origin`, `goal`. Existing image preparation marks all-black processed pixels as obstacles; never invert this interpretation accidentally.

## Coordinate, controller, and protocol conventions

- Screen arrays use row=y, column=x. Capture is BGRA. `match_img` returns desktop center by adding global capture `RECT.left/top`; `match_img_ltrb` returns ROI-local `(top_left,bottom_right)` with exclusive right/bottom. The fire caller adds (370,200) itself. Generic cropped center matching does not add crop offset, so its legacy desktop mapping is incomplete.
- Client baseline is 1280×720, UI 100%, primary monitor, unchanged pixel size under DPI, simplified Chinese game templates. Russian program messages do not imply Russian game recognition. `README.md` explicitly requires standard Esc/Enter/arrows/W/S/Shift/X/Space and mouse actions. Assets must remain verbatim.
- Fire ROI=(370,200,910,510); fallback lock ROI=(890,380,960,420); ammo ROI=(480,660,520,690); turret ROI=(85,545,145,615); collision mask uses full-height middle horizontal third. Fire HSV bounds=(33,109,149)…(137,255,255); turret green=(35,43,46)…(77,255,255); black lock=(0,0,0)…(180,255,46); collision red=(0,43,46)…(10,255,255).
- Tactical position is normalized x right/y down and converted using `int(value*128)` in legacy navigation. Heading is `degrees(atan2(dx,-dy))`, north=0, east=90, south=180, west=270. Turret helper returns a signed offset approximately (-180,180]. Search adds hull heading and turret offset. Use shortest signed target-minus-current error; specification chooses -180 for a half-turn tie.
- `pilot` uses `-PID_X(current_heading)` with target setpoint, so positive target-minus-current tends toward positive vJoy Z. Pixel aiming similarly negates PID with setpoint zero, giving positive mouse movement for positive screen displacement. Angular search does **not** negate PID and therefore has the opposite algebraic sign; retain and document boundary sign separately, pending manual game validation rather than silently inferring identical sensitivity/sign.
- vJoy device=1. X/Y/Z neutral=16384 with legacy signed range 0…32768 for requested -100…100; throttle RY neutral=0 with range 0…32768 for 0…100. Required physical-range validation must use the backend's actual supported range. Buttons 1–8 release on reset. Only Z steering is actively used by navigation; startup resets X/Y/Z/RY/buttons. Comments call buttons 1–5 flaps/airbrake/gear/brake/damper but naval gameplay does not use these methods.
- Mouse positive x=right, positive y=down; positive wheel=up. Search uses X, zoom uses Shift and right-click, firing uses left-click, navigation uses Z, battle init taps S three times, recovery holds S then W. All these need tracked ownership; static release lists are insufficient.
- `info` selects `icon=Player`, uses `map_info.valid`, scale=`int(map_max[0]-map_min[0])`, grid step=`grid_steps[0]`. Its hostile list is `icon=Ship` and `color[]` equal to `[250,12,0]` or `[240,12,0]`; legacy targeting instead uses `type=ground_model` with red hue. Capture zones are `icon=capture_zone` and color unequal to `[23,77,255]`. Preserve exact protocol spellings and record classifier reconciliation explicitly.
