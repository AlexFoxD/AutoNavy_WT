## Runtime and M6 integration contracts

Application(settings, *, telemetry=None, clock_ns=monotonic_ns, input_backend=None, window_guard=None, vision=None, navigation=None, rng=None, wait=None) is inert at construction. Defaults: recording backend unless enable_input; WindowsBackend and live F8/F9 hooks only on explicit live startup. CLI already requires --enable-input even if config enables input; replay rejects physical input. All required templates validate before capture; telemetry starts after capture; input starts after these prerequisites. Default wait is stop_event.wait; injected clock/wait make replay schedules deterministic. Direct tick(packet=None) is externally clocked; run uses it and enforces configured ready-source decision cadence, no backlog. CaptureTimeout still ticks existing holds and sequence/data expiry. Tick timing is cooperative, not a hard OS real-time guarantee.

The full-cycle test is a clearly labeled synthetic scripted capture double supplying FramePackets, an injected observation provider and immutable M4-shaped telemetry. It executes the real Application.run, BattlePolicy and InputController through waiting/queue/spawn/player/settle/initial S taps, ammo baseline, aim/fire, S3/wait60/W5/Sx3/wait10 recovery, back/return, purchase pause/resume and emergency stop. Separate tests exercise the actual selected VisionPipeline and matcher counts (battle <=15 matches without ammo baseline; menu <=28); every required asset remains validated and cached. These are not recorded gameplay or evidence of live recognition accuracy.

BattlePolicy.navigation is an optional M6 object with tick(app, observations, snapshot) and reset(). The actual battle path calls tick with fresh current values; pause/recovery/end/source/geometry/session/freshness invalidation invokes reset. M6 may submit steering using app.policy.emit('navigation','axis','Z', value, hold_s), which constructs current owner generation/source/geometry/session/TTL identity; or construct InputIntent explicitly with app.input.generation(owner). Zero releases only the same owner's tracked resource. Positive axis values map above configured neutral; source-equivalent steering must use negative heading target-minus-current error (coordinator's corrected AUDIT). Search uses positive shortest signed angular target-minus-current error, matching source; separate proportional aim/search outputs are currently used, with M6 responsible for independent PID state and ordered/native route policy. If M6 introduces a resource-owning route worker, add its owned close after input neutralization in Application cleanup.

InputIntent carries owner/action/resource/value, creation/dispatch deadline, duration, priority, owner cancellation generation, source generation, geometry identity, telemetry generation and telemetry declaration. InputController.submit/tick/cancel(owner=None)/release_all/start/close own every physical dispatch. Modes ui/battle/recovery/paused are exclusive; recovery cancels battle ownership; global cancellation epoch invalidates even issued-but-not-submitted tokens. Pending newest-value entries are bounded at settings.input.max_pending. Actual holds are recorded before an OS call so a partially applied failure remains retryable. Failed releases attempt all other holds and retain failed entries in input.held with input.release_errors; input.close can be retried. Do not relinquish vJoy before neutralization succeeds. Application preserves shared cleanup completion/error semantics and attempts capture/telemetry even if input/hook cleanup fails. Application's historical close error remains reported; failed held input can be retried through the exposed input owner.

Guards use the current service snapshot, not just retained data: all non-UI owners need a fresh Player/session, regardless of intent flag. All acquisitions require fresh current frame/source/profile identity. Physical dispatch additionally queries current Win32 geometry/focus, compares packet mapping and rechecks age/source/stop after that query. Releases are allowed even with failed acquisition prerequisites. Source/session/focus/profile changes cancel dependent sequences on the next tick. Menus deliberately ignore missing Player/generation changes; image/source/geometry safety still applies. Purchase markers and end markers remain selected in every state and purchase detection precedes battle Player gating. Generic cart alone does not pause; the audited start+cart combination does.

WindowsBackend preserves dependency FAILSAFE, sets PAUSE=0 only during explicit startup and restores it during cleanup. Key-up uses the dependency's undecorated release implementation, preserving its SendInput count check while allowing corner-emergency release; key-down retains failsafe checks. PhysicalPointer uses typed SetPhysicalCursorPos(INT,INT)->BOOL with signed negative desktop coordinates and checks failure. Wheel signs use complete five-argument mouse_event calls; zero wheel is a true no-op. Mouse_event has no acknowledgment return; fake transport validation does not prove the game received events.

OwnedVJoy queries actual axis existence/ranges and button count before acquisition. One lazy SDK device is acquired, abstract signed axes map around configured neutral to actual bounds, throttle zero maps to actual minimum, and buttons1-8 are neutralized. Explicit typed VOID RelinquishVJD avoids installed pyvjoy._sdk's incorrect return-value check and VJoyDevice destructor double release. The official source is https://github.com/shauleiz/vJoy/blob/master/inc/vjoyinterface.h . DLL discovery deliberately stays with installed/frozen pyvjoy._sdk._vj: its module locates utils/x64/vJoyInterface.dll beside the package. M8 must preserve that existing pyvjoy package/DLL layout in the Nuitka distribution and exercise fake import/packaging smoke; no new driver/DLL installer or global path configuration was added.
